# Rus-Trader

Автоматизированный торговый бот для российского фондового рынка (MOEX). Собирает рыночные данные (топ-50 ликвидных акций TQBR, часовые свечи, новости), анализирует их через DeepSeek R1 и автоматически исполняет сделки через T-Invest API.

## Архитектура

```
MOEX ISS API → топ-50 тикеров по объёму (TQBR)
      ↓
T-Invest SDK → резолв тикеров в UID, проверка tradability
      ↓
T-Invest SDK → часовые свечи за неделю (параллельно)
      ↓
MOEX ISS API → новости за 24ч → фильтр по тикерам
      ↓
T-Invest SDK → текущий портфель
      ↓
Indicators   → RSI(14), EMA(9/21), ATR(14), RelVol, S/R уровни
      ↓
Screener     → фильтрация тикеров по силе сигнала
      ↓
DeepSeek R1  → анализ индикаторов + OHLCV + новостей → JSON решения
      ↓
TradeGuard   → pre-validation (RSI > 80, время суток, лимиты)
      ↓
Executor     → лимитные ордера + SL/TP + trailing stop
      ↓
SQLite + Telegram + Web Dashboard
```

**Стек:** Go, T-Invest API (gRPC), MOEX ISS API, DeepSeek R1, SQLite (GORM), Telegram Bot API

## Торговые улучшения

### Технические индикаторы
Бот автоматически рассчитывает RSI(14), EMA(9), EMA(21), ATR(14), относительный объём и уровни поддержки/сопротивления для каждого тикера. Индикаторы передаются в AI для более точного анализа.

### Предварительный скрининг
Перед отправкой в AI тикеры ранжируются по силе технического сигнала (RSI-экстремумы, EMA-кроссоверы, аномальные объёмы). В анализ попадают только самые перспективные кандидаты.

### Trailing Stop
При включении (`trailing_stop_enabled: true`) бот автоматически подтягивает SL:
- При достижении 50% пути к TP — SL переносится на безубыток
- При достижении 75% пути к TP — SL фиксирует 50% прибыли

### Масштабирование позиций
Размер позиции зависит от уверенности AI: confidence 90+ = 100%, 80-89 = 75%, 70-79 = 50% от `max_position_rub`.

### Лимитные ордера
При `limit_order_slippage > 0` вместо рыночных ордеров используются лимитные с указанным отступом от текущей цены, что снижает проскальзывание.

### Фильтр по спреду
Перед покупкой проверяется bid/ask спред. Тикеры со спредом выше `max_spread_pct` пропускаются.

### Защита от плохих SL/TP
Executor автоматически корректирует решения AI:
- **Инвертированный SL** (SL >= цена входа) → пересчёт по `default_stop_loss_pct`
- **Слишком узкий SL** → расширение до динамического пола `max(min_stop_loss_pct, atr_sl_multiplier*ATR/price*100)` и жёсткий cap 6%
- **Слишком узкий TP** (< `min_take_profit_pct`) → расширение до минимума
- **Плохой R:R** (TP/SL < `min_risk_reward_ratio`) → увеличение TP

Динамический SL на основе ATR даёт широкий стоп волатильным тикерам (RUAL, WUSH) и не выбивает по рыночному шуму, а по спокойным оставляет минимум 2%.

### Фильтр инструментов, недоступных для API
Часть бумаг закрыта для торговли через API (флаг `api_trade_available_flag = false`) — например, под инфраструктурными ограничениями. Любой `PostOrder` по ним T-Invest отклоняет с кодом **30052** (`Instrument forbidden for trading by API`). Перед постановкой BUY/SELL/orphan-ордера Executor проверяет `broker.IsAPITradeAvailable` (результат кэшируется на время жизни процесса) и пропускает ордер, если торговля через API запрещена. Уведомление в Telegram отправляется **один раз на тикер за жизнь процесса** — это убирает шторм одинаковых ошибок и подсказывает, что позицию нужно закрыть вручную в приложении.

### Фильтр тренда
При `require_uptrend: true` TradeGuard блокирует BUY, если EMA9 < EMA21 (нисходящий тренд). Это предотвращает "ловлю падающих ножей" — покупку перепроданных бумаг, продолжающих падение.

### Pre-validation решений
TradeGuard механически блокирует BUY при RSI > 80 (перекупленность) и в последний час торгов (17:50-18:50 MSK).

### Circuit Breaker
При превышении дневного убытка (`max_daily_loss_rub`) бот прекращает открывать новые позиции до следующего дня. Защищает от каскадных потерь в неудачные дни.

### Фильтр убыточных тикеров
Тикеры, по которым были убытки за последние N дней (`recent_loss_cooldown_days`), временно блокируются для покупки (по умолчанию 1 день, чтобы не выжигать половину ликвидного списка из-за одной неудачной сделки). Дополнительно `max_losing_streak_per_ticker` блокирует тикеры, по которым накопилось N+ убыточных сделок подряд — этот фильтр точечнее и не зависит от времени.

### Market Context
В промпт передаётся общий фон рынка: среднее изменение по всем анализируемым тикерам за 1/3/7 дней и режим (`uptrend`/`downtrend`/`range`/`mixed`). Помогает модели адаптироваться к общим условиям вместо опоры на жёсткие запреты.

### Фильтр волатильности
Guard блокирует BUY для тикеров с ATR < `min_atr_pct` — если дневная волатильность слишком низкая, тикер не может дать необходимое движение для целевого TP 3%+.

### Минимальный score скринера
Тикеры с техническим score ниже `min_screener_score` не попадают в анализ AI (кроме тикеров с открытыми позициями). Снижает число шумовых сделок.

### Pre-screen жёстких BUY-фильтров (до ИИ)
Перед `Screener` запускается `guard.PreScreenBuyable`: отсекает не-позиционные тикеры, которые заведомо не пройдут детерминированные BUY-фильтры (`min_atr_pct`, RSI > 80, `require_uptrend`, `cooldown_minutes` после SELL, `recent_loss_cooldown_days`, `max_losing_streak_per_ticker`). Освобождает слоты `max_analysis_tickers` под реально покупаемых кандидатов — ИИ не получает заведомо обречённые тикеры, что экономит токены и уменьшает количество блокировок пост-фактум. Позиционные тикеры никогда не отсеиваются — они нужны Position Manager для SELL/HOLD.

Чтобы пре-фильтр имел достаточный запас, индикаторы считаются для пула `candidate_pool_size` тикеров (по умолчанию `max_analysis_tickers * 3`). То есть: берём из MOEX top N, считаем индикаторы для ~60 торгуемых, пре-фильтр отсекает обречённых, `Screener` ранжирует остаток и берёт топ `max_analysis_tickers` → в ИИ уходят лучшие **реально покупаемые** кандидаты.

Также `guard.CanOpenNewPositions` проверяет глобальные гейты (`max_open_positions`, `max_daily_trades`, circuit breaker `max_daily_loss_rub`, `no_last_hour_buy`). Если открыть новые позиции в цикле нельзя — Screening Agent полностью пропускается, работает только Position Manager.

**Позиционные тикеры не уходят в Screening Agent.** `featuresList` (вход скрининга) строится только из не-позиционных кандидатов: усреднение существующих позиций — задача Position Manager, и в нисходящем тренде оно справедливо блокируется фильтром `require_uptrend`. Исключение позиционных тикеров из скрининга убирает этот класс шумных блокировок.

### Контекст серии убытков
AI получает информацию о текущей серии убыточных сделок подряд. При 3+ убытках подряд промпт содержит предупреждение о необходимости повышенной осторожности.

### Статистика в промпте
AI получает агрегированную статистику за 7 дней: win rate, средний профит/убыток, худшие тикеры — для более осознанных решений.

## Phase 1: Smart Trading Pipeline

### Текстовые признаки вместо OHLCV-таблиц
Вместо сырых числовых таблиц AI получает осмысленные текстовые описания:
```
SBER (305.20): аптренд (EMA +0.8%), рост 3+ дней (+4.2%), объём повышен (1.8x), RSI 58 — нейтральный, у сопротивления 308.50 (0.5 ATR), ATR 1.5%, дивиденд 8.2% (отсечка через 12 дн).
```
LLM работает с текстом значительно лучше, чем с таблицами чисел — меньше ошибок в интерпретации.

### Дивидендный календарь (SmartLab)
Бот парсит SmartLab (`smart-lab.ru/dividends/`) для получения дат отсечки, размера дивидендов и доходности. Дивидендная информация включается в текстовые признаки тикеров с предстоящей отсечкой (в пределах `dividends.lookahead_days`). Кеш обновляется раз в `cache_ttl_hours` часов.

### Два AI-агента вместо одного
- **Screening Agent** — анализирует рыночные данные и ищет BUY-кандидаты. Не видит портфель — фокус только на рынке.
- **Position Manager** — управляет открытыми позициями (HOLD/SELL). Не видит рыночные кандидаты — фокус только на портфеле.

Оба агента работают **параллельно** (через `errgroup`). Если один упал — другой продолжает работу. Результаты объединяются и проходят через Guard → Executor.

### Trade Journal с LLM Daily Review
При каждой сделке сохраняется **trade outcome** — гипотеза при входе, текстовые признаки на момент входа, причина выхода, результат, длительность удержания.

Утром в первый торговый цикл LLM анализирует закрытые сделки за предыдущий день и генерирует **3-5 структурированных уроков** (pattern → observation → recommendation + confidence).

Уроки с confidence `medium`/`high` инжектятся в промпты обоих AI-агентов, позволяя боту учиться на своих ошибках между торговыми днями.

Конфигурация:
```yaml
dividends:
  enabled: true
  cache_ttl_hours: 12
  lookahead_days: 30

journal:
  enabled: true
  max_lessons_in_prompt: 5
  max_lesson_age_days: 7
  min_trades_for_review: 1

ai_agents:
  screening:
    max_chars: 16000
    max_tickers: 20
  position_manager:
    max_chars: 8000
  journal_review:
    max_chars: 12000
    model: ""  # пустое = основная модель
```

## Phase 2: Data Enrichment

### Order Book Metrics
Бот запрашивает стакан L2 (20 уровней) для каждого screened тикера через T-Invest `GetOrderBook`. Вычисляет три метрики:
- **Bid/Ask Imbalance** — соотношение bid/ask объёмов (>1.5 = давление покупателей)
- **Spread** — bid/ask спред в процентах
- **Wall Detection** — крупные уровни (>=5x среднего) — "стенки" в стакане

Метрики добавляются в текстовые features: `"стакан: bid давление 1.8x, спред 0.12%, bid wall 298.50 (7.2x)"`.

### Sentiment Scoring
Новости (Finam, world) + посты с форума SmartLab прогоняются через LLM (дешёвая модель `deepseek-chat`) для оценки sentiment по каждому тикеру: от -1.0 (крайне негативный) до +1.0 (крайне позитивный).

Результат в features: `"sentiment +0.6 (рекордные дивиденды)"`.

### Vector Pattern Memory
При каждой сделке сохраняется embedding текстовых features через OpenRouter (`text-embedding-3-small`). При screening для каждого кандидата ищутся исторически похожие паттерны (cosine similarity) и их результаты.

В промпт Screening Agent: `"SBER: 5 похожих — 3 win (+avg 2.8%), 2 loss. WR 60%."`.

Конфигурация:
```yaml
orderbook:
  enabled: true
  depth: 20
  wall_threshold: 5.0

sentiment:
  enabled: true
  model: "deepseek-chat"
  forum_enabled: true

vectordb:
  enabled: false  # требует OpenRouter API key
  openrouter_api_key: "sk-or-..."
  embedding_model: "openai/text-embedding-3-small"
  max_similar_patterns: 5
  min_similarity: 0.7
```

## Phase 3: Pipeline Refactoring + Backtesting

### Scheduler Refactoring
Scheduler разбит на 9 файлов по ответственности (вместо одного ~1000-строчного файла):
- `scheduler.go` — struct, init, run loop (104 строки)
- `cycle.go` — runCycle orchestration + cycleState
- `data.go` — data fetching (order book, sentiment, stats)
- `features.go` — не отдельный файл, enrichData в cycle.go
- `agents.go` — AI agents + daily review
- `execution.go` — guard + executor + trailing stops + cycle snapshots
- `reconcile.go` — двусторонняя синхронизация БД с портфелем брокера: закрытие stale trades (позиция закрыта у брокера, но open в БД) и усыновление orphan-позиций (позиция есть у брокера, но не в БД — после ручных покупок, рестарта в момент записи или восстановления из бэкапа)
- `snapshots.go` — analysis logs, portfolio snapshots
- `helpers.go` — utility functions

### Cycle Snapshots
Каждый торговый цикл сохраняет полный snapshot: свечи, features, портфель, решения AI, новости, режим рынка. Это фундамент для будущего full-pipeline backtesting.

### Backtester CLI
```bash
# Базовый replay
go run ./cmd/backtest/ -config config.yaml -db data/rus-trader.db

# Сравнение параметров
go run ./cmd/backtest/ -config config.yaml -db data/rus-trader.db \
  --min-confidence 60 --min-rr 1.2

# JSON output для автоматизации
go run ./cmd/backtest/ -config config.yaml -db data/rus-trader.db --json

# Диапазон дат
go run ./cmd/backtest/ -config config.yaml -db data/rus-trader.db \
  --from 2026-04-01 --to 2026-04-15
```

Backtester прогоняет исторические BUY-SELL пары через guard с изменёнными параметрами и показывает: как изменился бы P&L, win rate, max drawdown. Поддерживает override для: min-confidence, min-rr, min-sl, min-tp, max-daily-loss, require-uptrend, min-atr.

## Phase 4: Надёжное исполнение и риск-контроль

Фаза родилась из аудита реальных сделок (5 месяцев, 420 сделок): главными источниками убытков оказались не решения AI, а исполнение — несрабатывающие стопы, битые цены песочницы и лот-баги.

### Стоп-вотчдог (`internal/scheduler/watchdog.go`)
Отдельный быстрый цикл (`stop_watchdog_interval`, по умолчанию 2 мин) сравнивает котировки открытых позиций с их SL/TP и **немедленно закрывает позицию рыночным ордером без участия AI**. Раньше пробитый стоп ждал следующего 15-минутного AI-цикла, и фактический выход происходил на 2–5% ниже стопа. Вотчдог игнорирует `min_hold_minutes` (это ограничение только для решений AI) и пропускает API-forbidden тикеры и аномальные котировки.

### Санити-чек цен исполнения (`internal/broker/orders.go`)
T-Invest API непоследователен: `ExecutedOrderPrice` может быть суммой сделки или ценой за акцию (песочница), а `GetLotSize` может упасть. Теперь расчётная цена исполнения сверяется с последней котировкой (допуск ±20%): выбирается правдоподобная интерпретация, при полной аномалии используется котировка. Это закрывает класс багов, из-за которых в БД попадали цены вида 0.23 ₽ при реальных 29.85 ₽ и PnL завышался в разы.

### Санити-фильтр рыночных данных
Тикеры с котировкой, изменившейся более чем на `max_price_deviation_pct` (по умолчанию 30%) за день, исключаются из цикла целиком — аномальные данные песочницы не доходят ни до AI, ни до ордеров, ни до вотчдога.

### Лот-фиксы
Два бага для бумаг с лотом >1 акции (проявились на BAZA, лот=10): расчёт количества лотов шёл от цены за акцию (позиция раздувалась в lotSize раз — покупка на 74 800 ₽ при лимите 10 000 ₽) и PnL считался по лотам вместо акций (занижение в lotSize раз). Оба исправлены.

### Лимит совокупного риска портфеля
Guard блокирует BUY, если суммарный риск Σ(вход−SL)×акций по открытым позициям плюс оценка риска нового входа превышает `max_portfolio_risk_rub` (по умолчанию 2000 ₽). До этого ограничивались только размер одной сделки и число позиций, но не сумма одновременных рисков.

### Фантомные шорты и «ручная продажа»
Позиции с отрицательным количеством (артефакты песочницы после продажи большего, чем было) исключаются из портфеля везде — они больше не мусорят контекст Position Manager. Позиции, запрещённые для торговли через API (код 30052), помечаются на дашборде бейджем **«⚠ ручная продажа»**.

### Свинг-горизонт вместо интрадей-чёрна
Статистика однозначна: удержания <4 часов давали winrate 13%, а >5 дней — 57%. Изменения:
- Горизонт в промптах обоих агентов: **2–10 торговых дней**.
- Убрано правило Position Manager «SELL после 2 дней без прогресса».
- `cooldown_minutes` по умолчанию 7200 (5 суток) — повторные входы в тот же тикер в первые дни стабильно убыточны.
- `min_hold_minutes` по умолчанию 240 (вотчдога не касается).

### Правила риска в промптах
Screening Agent теперь получает реальные правила риска из конфига (размер позиции, SL-floor/кэп, минимальный R:R, circuit breaker, лимит совокупного риска) — модель предлагает SL/TP в рамках, которые код всё равно применит, вместо «вслепую».

### Метрики на дашборде
Profit Factor, Max Drawdown, Win Rate, средний плюс/минус, средний «проезд стопа» (насколько ниже SL фактически закрылись сделки) — по закрытым сделкам из БД.

## Торговые часы

Бот активен в торговые часы MOEX: **10:00–18:50 MSK**, понедельник–пятница.

## Режим песочницы

По умолчанию бот работает в sandbox-режиме. Аккаунт создаётся автоматически и пополняется на 1,000,000 руб. Stop-ордера в sandbox не поддерживаются T-Invest API — их роль выполняет стоп-вотчдог (см. Phase 4), который закрывает пробитые SL/TP рыночным ордером.

Для перехода на реальную торговлю установите `tinkoff.sandbox: false` и укажите `tinkoff.account_id`.
